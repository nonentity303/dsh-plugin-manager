## 1. 环境与隔离设计

| 项 | 值 |
|---|---|
| 克隆 profile（真实安装目录） | `<clone>`（= `C:\Users\<user>\Documents\harness\.dsh-tmp\verify-090\profile`） |
| 独立 DSH_HOME | `<workspace>\.dsh-tmp\verify-090\home` |
| profile 名（`dsh --profile` 只接受名字） | `verify090`，经 junction `home\profiles\verify090 → ..\..\..\profile` 解析（`linkType=Junction`，`Test-Path …\package.json` = True） |
| 引擎端口 / 启动器端口 | **3086** / **3087**（守护锁端口 4087 未使用） |
| 独立 pnpm store | `.dsh-tmp\verify-090\pnpm-store\v11`（真机 store 380 MB 的**工作区内副本**，因为沙箱只允许写工作区） |
| 真机端口 | 3080 引擎(pid 9600) / 3081 启动器(pid 29984) / 4081 锁(pid 12748) —— **全程未停、未重启** |

克隆内容（字节级复制）：`package.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml`、`cordis.yml`、`cordis.patch.yml`、`plugin-manager.json`、`.plugin-manager/`、`.dsh-market/`、`node_modules/`（73.1 MB，91 个顶层目录）。**没有**复制 `.open-boot.pid` / `.rescue-daemon.pid` / `.vbs` / 日志，避免把真机进程身份带进隔离环境。

> 为什么用 junction 而不是直接把 profile 放在 `.dsh-tmp/verify-090/home/profiles/verify090`：
> `dsh --profile` 的 `resolveProfileDir()` 明确拒绝含 `/` 或 `\` 的名字（`dsh: invalid profile name`），所以**契约里「`--profile <绝对路径>`」的写法在 DSH 0.1.7-rc.2 上不可用**，必须用「独立 DSH_HOME + profile 名」。junction 让两条路径指向同一个物理目录，兼顾契约里的路径与 CLI 的实际要求。

## 7. 独立发现（只记录，未改任何实现）

**F1（中，已验证，非新 bug）真机安装的字节 ≠ npm 发布的字节。**
真机 `~/.dsh/profiles/web/node_modules/dsh-plugin-manager-pro/lib/client.js` = **976,145 B / `B8D08B66F070409799D72CC0C2B7DAC692740E209B0E623AF2A62A3BE8D6CFDF`**；npm 发布件（= vendor tgz = 仓库构建）= **782,481 B / `547E8D75…`**，差 194 KB。这正是 `docs/RELEASING.md` §2bis 记载的 **pnpm 依赖树（zod 4.5.4）vs npm ci 树（zod 4.4.3）** 差异（F5 同族），不是新缺陷。队长已确认处理方式：**上传前不动真机**，等 0.9.1 由 CI 发布后把真机 profile 重装为发布件并核对 bundle 哈希。

**F2（低，已知）启动器的引擎端口是硬编码常量。**
`lib/enginectl.mjs:27 export const ENGINE_PORT = 3080`；`bin/open-boot.mjs` 的 `--status`、`/api/status`、健康判定都用它，**启动器自身的 `--port` 只影响启动器监听端口**。后果：在隔离端口（3086/3087）做验证时，启动器上报的引擎状态说的是 **3080 那台**；多引擎/多 profile 场景下会给出与当前 profile 无关的引擎结论（审计 R7「端口分工」相关）。本次报告已按此口径解读 §4。

**F3（低，环境陷阱）克隆 profile 不能直接沿用 `pnpm-lock.yaml` 的相对 `file:` 规格。**
真机 lockfile 里 `file:../../../Documents/harness/migration/...` 是相对**真机 profile 深度**的路径；克隆目录深度不同 → pnpm 解析出 `…\harness\Documents\harness\migration\…` 并 `ENOENT`。建议后续克隆验证统一：`node_modules/.pnpm/lock.yaml` 与项目 `pnpm-lock.yaml` 一并清理后再装（只删项目那份不够——pnpm 会用虚拟 store 里那份复原）。

**F4（低，环境陷阱）`pnpm add <pkg>@<同版本号>` 可能不改动包目录内容。**
首次「成功」的 `add`（`+1 -4 +-`、exit 0）只更新了 `package.json`/lockfile，`node_modules/dsh-plugin-manager-pro` 里仍是被克隆进来的旧字节（976,145 B）。**同名同版本、内容不同**时只比版本号会得出错误结论——与 F5 的教训同构。克隆/迁移验证一律要**比内容哈希**。

**F5（观察，非我造成）真机 profile 的 `cordis.patch.yml` mtime = 2026-10-06 11:59:50（本会话期间）。**
不是本任务写的：① 本次唯一一次触到真机 profile 的命令（`dsh plugin --profile web --help`，早期探索）在**写 `package.json.lock` 时被沙箱拒绝**（`EPERM: operation not permitted, open '…\profiles\web\package.json.lock'`），证明沙箱不允许我写那里；② 文件大小（8252 B）与开始测试时一致、首行内容一致、且其中**没有** `ui-plugin-manager` / `ui-settings-plugin-inventory` 条目（与 0.9.0 的设计一致）。同一时刻还有 `.open-boot.pid`（11:59:20）、`cordis.yml`（11:59:23）、`.rescue-daemon.pid`（11:59:39）被更新，看起来是该时段**引擎/启动器自身的 profile 状态改写**（或用户/其它成员操作），供队长判断是否需要追。

**F6（中，发生于本会话验证窗口内）仓库 `lib/client.js` 被重建 → vendor/发布件与工作树不再一致。**
- 14:0x（attempt 1 验证时）：`plugin-manager/lib/client.js` = 782,481 B / `547E8D75…`，与 registry tarball、vendor tgz **完全一致**。
- 14:2x（attempt 2 复核时）：同一路径 = **792,931 B / `00D06285C668611DEBFBBC106B94C07CFF9D56A7F83119ED98BA1AEFC6AD321D`**（+10,450 B），而工作区里的 registry 发布件（`.dsh-tmp/verify-090/registry/`）与 `migration/pkg/main/vendor/dsh-plugin-manager-pro-0.9.0.tgz` **两份都没变**。
- 判断：**其它成员进行中的 0.9.1 改动**（或某次 `npm test` 触发的 `node build.mjs`）造成的正常开发漂移，**不是**发布件被篡改，**不影响**本报告对 npm 0.9.0 的结论。
