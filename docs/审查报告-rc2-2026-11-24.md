## ② 问题清单

### P0（阻断发布）

#### P0-1 重启引擎 = 无条件 `force` + `taskkill /T /F` 树杀，PID 复用时可杀任意进程树

- **位置**：`bin/open-boot.mjs:1669`（`stopEngine(args.profile, { force: true, port: ENGINE_PORT })`）；`lib/enginectl.mjs:584-590`（`force` 跳过全部 4 项身份校验）、`lib/enginectl.mjs:592-602`（`taskkill /PID <pid> /T /F`）
- **现象**：
  1. `force:true` 让 `stopEngine` 里 `reasons` 全部失效——pid 复用、映像名不符、端口占用者不一致、PID 文件无 app 标记，**一条都拦不住**；
  2. `/T` 连带杀掉该 pid 的整棵子树。
- **触发条件**：
  - 引擎崩溃/被强杀后留下陈旧 `.rescue-daemon.pid`，其 pid 被系统复用给任意进程 → 用户在 3081 兜底页点「重启引擎」（`bin/open-boot.mjs:2231`）→ 直接 `taskkill /T /F` 那个无关进程树；
  - 今天已真实发生：测试实例挂在引擎进程树下，一次重启被一锅端。
- **附加矛盾**：同一仓库内 `bin/open-boot.mjs:17/329/1079/1195` 三处注释与 README 都写"**绝不** `taskkill /T` 整棵树"，`stopOwnedPid`（`bin/open-boot.mjs:1146` 附近）确实只用 `process.kill(pid)`——唯独 `stopEngine` 例外，且作者自己踩过坑（审计③ 装机教训）。
- **修复建议**：
  1. `restartEngine` 不要传 `force:true`；校验不过就返回失败并提示人工确认（或要求二次确认 + 显式 `force` 请求体）；
  2. `taskkill` 去掉 `/T`，只杀引擎 pid；确实要清子进程时，用 `Get-CimInstance Win32_Process` 枚举 `ParentProcessId` 子进程，**逐个**校验映像名=node 且命令行含 profile 路径后再杀；
  3. 身份校验补 `startedAt`↔`CreationDate` 比对（见 P2-7），把"pid 复用"从概率问题变成确定可判。

> 注：该逻辑是 rc.1 已有代码，**不是本次 diff 引入**；但 rc.2 在重做的兜底页里把它做成一级按钮（带一次确认框），触发面显著变大，且今天已产生真实损失，故按 P0 计。

### P1（严重）

#### P1-1 `removePatchEntriesFor` 的匹配串对真实 patch 格式静默失效（清 patch 步骤谎报成功）

- **位置**：`bin/open-boot.mjs:1478`（`const needle = \`name: ${pkgName}\``）、`:1490-1494`（`chunk.some(line => line.includes(needle))`）、`:1563`（无论实际删了几个都 `step("patch-cleanup","ok",...)`）
- **现象**：真实 `~/.dsh/profiles/web/cordis.patch.yml` 里两种写法都不匹配：
  - **带引号**（loader 对 scoped 包的写法）：`  name: "@deepseek-ai/dsh-client-ui-settings-general"` —— needle `name: @deepseek-ai/...` 少了引号，**永不命中**；
  - **只有 id、没有 name 字段**：`- id: dsh-whale-widget` / `  disabled: false`（正是管理器自己写的那一行，见该文件 254-256 行 `#Managed by dsh-plugin-manager-pro`）——**永不命中**。
  只有 `name: dsh-vision-router` 这种**无引号**写法才会被删（该文件 249-250 行）。
- **触发条件**：卸载任何 scoped 包（`@scope/x`，实测本机 profile 有 3 个）或任何"只有 id"的补丁行 → `removed:0`，但 UI「操作步骤日志」显示 `✔ patch-cleanup`，README 也宣称已清理。
- **真实后果**（已核对引擎侧实现）：残留条目只会触发 `dsh-app-boot` 的 `warn("patch: entry %C not found", id)`（`dsh-app-boot/lib/index.js:541-547`），**不会炸启动**，但：① 残留配置在插件重装后会被重新应用（幽灵配置）；② 每次启动多一条告警；③ 用户/文档误以为已清理。
- **修复建议**：
  1. 把启发式改成"块内出现 `^\s*(-\s+)?(name|id):\s*["']?<escaped pkg>["']?\s*$`"，用 `RegExp` + 转义包名，**必须**吃引号与 `id:` 两种形态；
  2. 同时容忍 flow-style JSON（loader 可能重写成 `[{...}]`，见开发指南 §"cordis.patch.yml"），块解析失败时**回报 `ok:false` 而不是 ok**；
  3. `step("patch-cleanup")` 按真实结果分级（`removed===0 && total>0` 时给 warn + 明确"未找到归属条目，请人工确认"）；
  4. 顺手把函数导出（或移到 `lib/patch-clean.mjs`）以便单测（见 ④）。

#### P1-2 卸载不摘 `dsh.profile.bundles` → 留下悬空 bundle 声明（与引擎侧实现不一致）

- **位置**：`bin/open-boot.mjs:1503-1579`（整个 `uninstallPackageTransactional`，全函数只动 `dependencies` / patch 文件）；对照 `lib/index.js:2114-2117`（引擎侧 `uninstallPackages` **会** `bundles.filter(b => !removal.includes(b))`，并在失败时 `pnpm` 重装回滚，`lib/index.js:2186-2203`）
- **现象**：`pnpm remove` 只改 `package.json` 的 `dependencies`，`dsh.profile.bundles` 是自定义字段、原封不动。卸载完成后：
  - `listBundles` 取 `installed ∪ enabled`（`bin/open-boot.mjs:1393`）→ 该包仍以 `enabled:true` 显示在页面上；
  - 引擎下次启动 `loadProfileDirectory` 解析不到包 → `skippedBundles` + stderr 输出 `skipping profile bundle "x": cannot resolve ...`（已核对 `dsh-app-boot/lib/index.js:1789-1834`，**不炸启动**，所以是 P1 而非 P0）；
  - `verify` 步只测 `pnpm ls`，**从不检查 bundles 与 patch**，却打出"清单与 patch 均已处理"（`:1567`）。
- **触发条件**：引擎未运行（或握手超时，见 P1-3）时，卸载一个**处于启用状态**的包 —— 这正是"用 3081 兜底页救火"的典型状态。
- **修复建议**：在 `pnpm remove` **成功之后**复用 `setBundleEnabled(profile, pkgName, false)`（它自带备份 + 原子语义），或在同一事务里显式 `manifest.dsh.profile.bundles = bundles.filter(...)`；回滚路径也要把 bundles 恢复。顺序建议：备份 → 摘 bundles（含备份）→ pnpm remove → patch → verify。

#### P1-3 EBUSY 半删防护 fail-open（一次握手超时即放行硬删）

- **位置**：`bin/open-boot.mjs:1513`、`:1613`（`const engine = await engineHealth(ENGINE_PORT)`），判定 `if (engine.ok && enabled.includes(pkgName))`（`:1515`、`:1615`）
- **现象**：`engineHealth` 是 1.5s 超时的 HTTP 握手（`lib/enginectl.mjs:101`）。机器负载高 / 引擎刚启动 / GC 停顿时握手失败 → `engine.ok=false` → **保护被跳过**，直接 `pnpm remove` 正在被引擎占用的 `node_modules` → Windows `EBUSY` 或半删，正是该保护要防的事。
- **触发条件**：引擎在跑 + 一次 1.5s 握手失败。本仓 `boot()` 里已经踩过同款坑（`bin/open-boot.mjs:578-600` 专门为此加了"端口有 node 监听就先等握手"的逻辑），说明这个失败模式在本机是真实存在的。
- **修复建议**：`engineHealth` 之后追加 `await probe(ENGINE_PORT)`：**端口有人就拒绝**（不管握手成不成），文案改成"端口 3080 有监听者，无法确认引擎是否已停；请先停止引擎或确认后强制"。更新接口同理。

#### P1-4 `runPnpm` 超时只杀 `cmd.exe`，pnpm 进程树存活继续改 `node_modules`

- **位置**：`bin/open-boot.mjs:1454-1466`（`exec(cmd, { timeout })`）
- **现象**：`exec` 的 `timeout` 只 `TerminateProcess` 直接子进程（Windows 上是 `cmd.exe`），`pnpm.cmd → node` 孙子进程存活。于是：API 已经在 `:1550-1558` 判定"超时/失败 → **已回滚清单**"，而后台 pnpm 仍在写 `package.json` 与 `node_modules` → 清单与磁盘互相覆盖，产生**真正的半删状态**，且回滚内容随后又被 pnpm 覆盖。
- **触发条件**：`pnpm remove/update` 超过 180s（大包、弱网、store 锁竞争；本机 `minimumReleaseAge`/allowScripts 相关卡顿已有先例）。
- **修复建议**：改用 `spawn` 拿到 pid，超时后 `taskkill /PID <pid> /T /F`（**这里是自己的 pnpm 子树，可安全 /T**）或 `spawn(..., {detached:true})` + 杀进程组；超时后**不要**立刻回滚清单，而是先确认 pnpm 已死（或直接返回 `state:"unknown"` 让用户检查）。

#### P1-5 自卸载后提示的补救命令已不存在（自启残留无法按提示清理）

- **位置**：`bin/open-boot.mjs:1522-1526`（self-warning）、`:1574-1575`（卸载成功文案："之后请运行 node bin/open-boot.mjs --uninstall"）、`:1943`（页面底部提示长文案同样指引）
- **现象**：管理器自身装在 profile 的 `node_modules` 里（本机实测 `dependencies.dsh-plugin-manager-pro = file:E:/harness/.../dsh-plugin-manager-pro-1.0.0-rc.2.tgz`），`pnpm remove` 成功后 **`bin/open-boot.mjs` 文件本身已被删除**，`node bin/open-boot.mjs --uninstall` 必然 `MODULE_NOT_FOUND`。而 `HKCU\...\Run` 的 `DSHWebFront` 仍指向 `~/.dsh/scripts/dsh-open-boot.vbs/.cmd`（那套 shim 是启动器每次启动重写的），下次开机仍会尝试拉起一个已删除的包。
- **触发条件**：在 3081 页面对管理器自身点「卸载」并确认。
- **修复建议**：自卸载时**先**在进程内执行 `uninstallAutostart(args)`（`bin/open-boot.mjs:1044` 已存在）+ 删除 shim，再 `pnpm remove`；或把 shim 写到 `~/.dsh/scripts/` 里自包含（不依赖包路径）。文案同步改成"自启已自动清理"。

#### P1-6 `/plugins/api/health`、`/plugins/api/updates` 是无令牌 GET，且 `health` 全量同步读 `web.log`

- **位置**：`bin/open-boot.mjs:2383-2387`（updates GET，无 `rejectWrite`）、`:2408-2412`（health GET，无 `rejectWrite`）、`:1643`（`readFileSync(webLogPath(), "utf8")` 全量读入后 `.split(/\r?\n/).slice(-300)`）
- **现象**：
  1. **鉴权**：`/api/status`、`/api/bundles(GET)` 不加防护是设计如此（"读取类接口不加防护"，`lib/enginectl.mjs:623`），但新增的两个 GET **有副作用/开销**：`updates` 每次拉起一个 `pnpm outdated`（网络 + store 锁，最长 120s），`health` 每次同步 `readFileSync` 整个 `web.log` + `verifyProfile`。任意网页用 `<img>` / `fetch(mode:"no-cors")` 即可反复触发（响应读不到，副作用照旧）——与审计③ L11 修掉的那类问题同构。
  2. **阻塞**：启动器是单线程 HTTP 服务；`web.log` 无上限（本仓 `lib/enginectl.mjs:350-372` 的 `readLogTail(maxBytes)` 已经把"读日志要限字节"做对了，这里却退回全量读）。日志涨到数百 MB 时，单次 `health` 会占住事件循环数秒 → `/api/status` 1.5s 超时 → `ensureServer`/`launcherHealthWithRetry`（`bin/open-boot.mjs:429`、`:2487`）可能把"自己的实例"误判为"别人的进程"，触发误导性告警甚至拒绝启动分支。
- **触发条件**：`web.log` 变大（本机当前 0 字节，但 3080 每次启动都追加 stdout，长期必然增长）；或任意本机/浏览器页面反复打 GET。
- **修复建议**：① 两处 GET 也加令牌校验（页面已带 meta token，改造量极小；`/api/status` 保持免鉴权以不破坏 `launcherHealth`）；② 读日志改成"先 `statSync` 取 size → 只读末尾 `min(size, 256KB)`"（复用 `enginectl.readLogTail` 的思路），并 `await` 前先 `readFileSync` 换成异步；③ `healthReport` 加 30s 结果缓存，避免重复爬日志。

### P2（一般）

#### P2-1 卸载/更新没有单飞闸门，并发会互相踩
- **位置**：`bin/open-boot.mjs:2398-2406`（uninstall）、`:2388-2396`（update）、`:1669`（对比：只有 restart/boot 走 `flight.tryEnter`）
- **现象**：同一 profile 下并发两个 `pnpm remove`（两个标签页 / 一个页面两行连点 / 脚本）→ pnpm 锁竞争、`package.json` 后写覆盖先写、`backupProfileManifest` 同毫秒同名互覆；`uninstall` 与 `POST /plugins/api/bundles`（`setBundleEnabled` 读→写 `package.json`）也会丢更新。
- **建议**：`/plugins/api/{uninstall,update}` 复用同一个 `createSingleFlight`，第二个请求回 409（页面已有 409 文案可复用）。

#### P2-2 "verify" 步验证的不是后置条件，判定也脆弱
- **位置**：`bin/open-boot.mjs:1565-1570`
- **现象**：成功条件 `verify.code === 0 && !verify.stdout.includes(pkgName)`；`pnpm ls <不存在的包>` 通常会以非 0 退出，此时会命中 else 分支打出 **"pnpm ls 仍列出 X"**（与事实相反）；而真正该断言的（`dependencies` 已无该键、`dsh.profile.bundles` 已摘除、patch 已清）一个都没查 → 与 P1-1/P1-2 叠加后，前三步全错也会报 `ok:true`。
- **建议**：`verify` 改为读 `package.json` 断言 `!(pkgName in dependencies)`、断言 `bundles` 不含它、断言 patch 里无归属块；任一不满足 → `ok:false` 并进入回滚分支。

#### P2-3 `package.json` 写入非原子（含回滚写）
- **位置**：`bin/open-boot.mjs:1554`（回滚整体覆盖写）、`:1421`（`setBundleEnabled`）、`:1514` 相关
- **现象**：直接 `writeFileSync` 目标文件。断电/杀进程/磁盘满时留下半截 JSON → profile 清单损坏 → 引擎起不来（本仓开发指南里"BOM/坏 JSON 导致 boot 失败"是血泪教训）。备份文件是另一路径，恢复需手工。
- **建议**：写临时文件 + `renameSync` 原子替换（`~/.dsh` 里已有 `@deepseek-ai/dsh-atomic-write` 可参考实现）；回滚路径同样。

#### P2-4 mod 体检丢掉非 bundle 的 preflight 问题 → 失败页显示"全绿"
- **位置**：`bin/open-boot.mjs:1637`（把 `verify.issues` 全量塞进 `issues`）、`:1652-1661`（只按 `b.name` 匹配）
- **现象**：`verifyProfile` 除了"bundle 不可解析"，还会报 `name: "package.json"`（清单解析失败）与 `name: "cordis.patch.yml"`（YAML 解析失败/不是顶层数组）（`lib/preflight.mjs:20-70`）。这些名字匹配不到任何 bundle → 从 `rows` 里消失；页面 `runHealth` 只渲染 `r.rows`（`bin/open-boot.mjs:2200-2216`）→ 用户看到"每行都是 ok"，而 profile 实际处于"boot 必失败"状态。
- **建议**：`rows` 之外单独渲染 `issues`（页面加一个"全局问题"区块），或 `ok = verify.ok && rows.every(...)` 并把 `ok:false` 显式呈现。

#### P2-5 生成脚本里的 ps1/CIM 身份校验是 fail-open
- **位置**：`bin/open-boot.mjs:1768-1771`（`for /f ... OWNER=%%a` → `if "%OWNER%"=="mismatch" ... exit /b 3` → `taskkill /T /F`）
- **现象**：只要 PowerShell/CIM 取不到结果（被策略拦、CIM 慢、`Get-CimInstance` 报错），`OWNER` 为空 → `""=="mismatch"` 为假 → **仍然 taskkill /T**。今天的 `/T` 连坐正好通过这条路径被放大。
- **建议**：改成**白名单**判定：`if not "%OWNER%"=="match"` → 拒绝结束并提示人工确认；同时 `:stop` 里的 `taskkill` 去掉 `/T`（与 `--uninstall` 的"绝不 /T"保持一致）。

#### P2-6 `stopEngine` 用旧 `portOwner`，丢失"探测失败"语义 → netstat 失败时跳过端口一致性校验
- **位置**：`lib/enginectl.mjs:571`（`const owner = portOwner(port)`，只返回 pid）、`:579`；对比 `lib/enginectl.mjs:139-166`（`portOwnerProbe` 明确区分 `ok:false` 探测失败）与 `bin/open-boot.mjs:1091/1124-1125`（本仓自己的归属校验已经改用 `portOwnerProbe` 并尊重 `ok`）
- **现象**：`netstat` 被拦/超时 → `owner=null` → "端口占用者必须等于记录 pid"这条校验**静默消失**；若 PID 文件恰是本工具写的（`info.app === PID_APP`），`reasons` 为空 → 直接杀。即：探测不可用 = 放行。
- **建议**：`stopEngine` 改用 `portOwnerProbe`，`ok:false` 时直接 `refused`（探测不可用 ≠ 端口空闲）。

#### P2-7 `startedAt` 写进 PID 文件却从不参与身份校验
- **位置**：`lib/enginectl.mjs:510-514`（写入 `startedAt`）；`lib/enginectl.mjs:565-582`（校验里没有它）
- **现象**：pid 复用的唯一防线是"映像名像 node + 端口占用者一致 + app 标记"。而 `node.exe` 遍地都是，`taskkill /T /F` 又是树杀 → P0-1 的根因。

#### P2-9 profile 目录里的备份文件无上限累积
- **位置**：`bin/open-boot.mjs:1539`（每次卸载写 `${patchFile}.uninstall-bak-<ts>`，**从不清理**）；对照 `backupProfileManifest` 有 5 份上限（`:1378-1383`）；`lib/index.js` 的 rescue/mods 备份同样无上限

#### P2-10 文档与实现不符：`README.md` 的"事务性卸载"描述过度承诺，版本/CHANGELOG 不一致

## ⑤ 结论：rc.2 能否安全发布？

**不能。** 必须修的 **P0 只有 1 项**：

- **P0-1** `restartEngine` 的 `force:true` + `taskkill /T /F` 树杀（`bin/open-boot.mjs:1669` + `lib/enginectl.mjs:584-602`）：PID 复用下会杀掉任意无关进程树，今天已真实连坐测试实例；且与仓库自身"绝不 taskkill /T"的既定红线自相矛盾。

同时强烈建议在同一个 rc 里修掉这 4 项 P1——它们直接决定 rc.2 的三个卖点是否成立：

- **P1-1** patch 清理对真实格式静默 no-op（scoped 包 / 只有 id 的块），步骤日志谎报成功；
- **P1-2** 卸载不摘 `dsh.profile.bundles`，留下悬空 bundle 声明（引擎侧 `uninstallPackages` 是摘的）；
- **P1-3** EBUSY 防护在握手超时时 fail-open，会让"先禁用再卸载"的引导形同虚设；
- **P1-4** pnpm 超时只杀 `cmd.exe`，pnpm 树继续改 `node_modules`，与"已回滚清单"直接矛盾。

若只想尽快发版：把兜底页的「卸载 / 更新」两个按钮先降级为"复制命令 + 指引先禁用"（只保留 P1-6 的鉴权修复 + P0-1），即可在不带 P1-1~P1-4 的情况下安全发布；否则请把上面 5 项一并修掉并补 ④ 中第 1-6 项测试。
