# 版本与轨道（dsh-drydock）

> 本文件回答一个具体问题：**「我要装/要看的是哪个版本，它给哪个端？」**
> 机器可读的事实来源是 [`release/channels.json`](../release/channels.json)；本文件是给人看的同一份口径。
> 两者由 `node test-channels.mjs` 强制对齐 —— 改一边不改另一边会 FAIL。

## 一句话模型

**一个包、一条版本序列、三条发布通道。**

- 包只有一个：`dsh-drydock`（`dsh plugin add` 装的就是它，桌面/网页共用同一份产物）。
- 版本序列只有一条：`X.Y.Z[-<通道>.<n>]`。**核心数字 `X.Y.Z` 只表达产品推进，不表达"给哪个端"。**
- 通道写在**预发布段**里：`-rc.N` = 网页预发布，`-desktop.N` = 官方桌面，`-community.N` = 社区桌面（当前占位）。
  历史沿用的 `-alpha.N` / `-beta.N` 也归 **web** 通道（在 `release/channels.json` 里登记为 `prereleaseAliases`）。

## 通道表

| 通道 | 通道全称（与 `channels.json` 的 `title` 逐字一致） | 版本形态 | npm dist-tag | 安装命令 |
|---|---|---|---|---|
| **web** | 网页 / 引擎宿主（主线） | 正式版 `1.0.5`<br>预发布 `1.0.5-rc.1` | `latest`（正式）<br>`next`（预发布） | `dsh plugin --profile web add dsh-drydock`<br>`dsh plugin --profile web add dsh-drydock@next` |
| **desktop** | 官方桌面宿主（Windows / macOS） | 预发布 `1.1.0-desktop.1`（**不单独发 GA**） | `desktop` | `dsh plugin --profile desktop add dsh-drydock@desktop` |
| **community** | 社区桌面发行版（占位）· 2026-11-27 决定暂不启用 | —（`enabled: false`） | `community`（保留未启用） | —（形态确定后再补） |

> ⚠️ **通道解析只靠 dist-tag，不要靠"取最高预发布版"**：semver 字典序里 `1.1.0-desktop.2 < 1.1.0-rc.2`
> （`desktop` < `rc`），所以用 `^1.1.0-rc.2` 这类范围去解析，可能永远装不到桌面通道的新版。
> 桌面试用一律用 `dsh-drydock@desktop` 或显式版本号。

## 版本号怎么升（判据是"改动性质"，不是"改的是哪个端"）

| 改动性质 | 核心版本 | 版本形态 | 示例 |
|---|---|---|---|
| 桌面 / 社区桌面**宿主升版适配**（只改适配与门控） | **不动** | 后缀 +1 | `1.1.0-desktop.1 → 1.1.0-desktop.2` |
| 共享代码修复（安全 / 核心 bug），各端都要 | patch +1 | 正式版 | `1.0.4 → 1.0.5` |
| 同一修复先给桌面尝鲜 | 跟随上式 | `1.0.5-desktop.1` | 同基线，两个通道 |
| 新功能（不分端） | minor +1 | 正式版或 `-rc.N` | `1.0.5 → 1.1.0` |
| 破坏性变更（宿主 API / cordis 适配断代） | major +1 | 正式版 | `1.x → 2.0.0` |

**三条纪律**

1. 核心数字只能被"产品推进"改，**不能被"宿主动了"改**。宿主升级 → 只动后缀。
2. 预发布标识必须**已登记**在 `release/channels.json`；写 `1.1.0-foo.1` 会被 `tools/dev/channels.mjs` 直接拒绝（不做静默兜底）。
3. 分支名 / tag / 版本号**不要三处写同一个数字**：分支只表达轨道（`track/desktop`、`release/1.0.x`），版本号只在 `package.json` 与 tag 里出现。

## 为什么不用 GitHub Packages 当主发行面

GitHub Packages 的 npm registry 有三个硬约束，与「DSH 插件用 `dsh plugin add` 安装」的消费路径冲突：

1. 只支持 scoped 包名（`@namespace/name`）→ 现有 `dsh plugin add dsh-drydock` 全部失效；
2. 公开包也**必须带 token** 才能装 → 每个用户都要配 `.npmrc` PAT；
3. 不接 npm 的 OIDC 可信发布（现 `release.yml` 走 `--provenance`，零长期 token）→ 供应链安全倒退。

它唯一合适的用法是**凭据门禁的内测分发**（把桌面通道 tgz 作为私有包发给少数测试者）。当前规模不需要，故不启用。
